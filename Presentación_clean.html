Clean Architecture en KMP

¿Por qué KMP + Clean Architecture?

🚀 KMP te da:

  • • Compartir lógica de negocio (Domain + Data)
  • • UI nativa en cada plataforma
  • • Un solo código para reglas de negocio
  • • Tests compartidos entre plataformas

🏗️ Clean Architecture organiza:

  • • Dependencias claras en shared code
  • • Tests unitarios sin plataforma
  • • Escalabilidad multiplataforma
  • • Mantenimiento simplificado

KMP comparte el "qué" (lógica) + Clean Architecture organiza el "cómo" (estructura)

El Problema Común en KMP

❌ Código KMP típico (sin Clean Arch) 

// shared/src/commonMain/kotlin
class ProductViewModel {
    private val api = KtorClient() // 🚨 Acoplado a Ktor
    
    fun loadProducts() {
        // 🚨 Lógica en ViewModel
        // 🚨 No se puede testear sin KMP
        // 🚨 Android/iOS necesitan saber detalles
    }
}

// androidMain/iOSMain
// ¡Duplicar lógica en cada plataforma!

✅ Con Clean Architecture + KMP 

// shared/src/commonMain/kotlin
class ProductViewModel(
    private val getProductsUseCase: GetProductsUseCase
) {
    fun loadProducts() {
        // ✅ Solo coordina UI
        // ✅ Lógica compartida 100%
        // ✅ Testeable sin plataforma
        getProductsUseCase()
    }
}

// ¡Un solo código para todas las plataformas!

Clean Architecture no es complicado, es organizado.

¿Cuándo usar (y cuándo NO) Clean Architecture?

✅ Úsala cuando:

  • • Proyecto mediano o grande
  • • Más de 2 desarrolladores
  • • KMP / Multiplataforma
  • • Reglas de negocio reales
  • • Necesitas tests confiables

❌ No es ideal cuando:

  • • Apps demo o prototipos
  • • CRUDs muy simples
  • • Apps de una sola pantalla
  • • Time-to-market ultra corto

Clean Architecture es una herramienta, no una religión.

¿Qué es Clean Architecture?

Es una filosofía de diseño que busca separar las reglas de negocio de los detalles técnicos.

Principio de Cebolla

Visualiza el software como capas concéntricas. La lógica de negocio está en el núcleo y las dependencias apuntan estrictamente hacia adentro.

Arquitecturas Similares

Hexagonal (Ports & Adapters) Onion Architecture Screaming Architecture DCI

Regla de Oro: Dependencias

El Dominio (centro) no debe conocer nada de la Base de Datos o la UI (afuera).

  • ❌ Compose

¿Qué pasa cuando el usuario abre una pantalla?

  1. ① La UI se muestra (Compose).
  2. ② El ViewModel pide datos.
  3. ③ El ViewModel llama a un Use Case.
  4. ④ El Use Case usa un Repository (contrato).
  5. ⑤ El Repository obtiene datos (API / DB).
  6. ⑥ Los datos se limpian con Mappers.
  7. ⑦ El dominio recibe modelos puros.
  8. ⑧ La UI se actualiza.

Ninguna capa rompe las reglas. Todo fluye hacia adentro.

Errores Comunes (y cómo evitarlos)

❌ Error #1: Lógica en ViewModel 

// MAL: ViewModel con reglas de negocio
viewModelScope.launch {
    val products = api.getProducts()
    val filtered = products.filter { it.price > 100 }
    val sorted = filtered.sortedBy { it.name }
    _uiState.value = sorted
}

✅ Solución: Mueve la lógica a un UseCase

❌ Error #2: Ignorar Mappers 

// MAL: Usar DTOs directamente en la UI
data class ProductDto(
    val id: String?, // Puede ser null
    val product_name: String // Nombre diferente
)

✅ Solución: Siempre mapea a modelos de dominio

❌ Error #3: Repository con implementación 

// MAL: Repository en Data layer
class ProductRepository(private val api: ProductApi) {
    suspend fun getProducts() = api.getProducts()
}

✅ Solución: Interface en Domain, impl en Data

❌ Error #4: UseCases con múltiples responsabilidades 

// MAL: UseCase que hace todo
class ProductUseCase {
    suspend fun getProducts() { ... }
    suspend fun saveFavorite() { ... }
    suspend fun deleteProduct() { ... }
}

✅ Solución: Un UseCase = Una responsabilidad

Domain: Repositories

Repository Interface

¿Qué es? Es un contrato. Define qué datos necesita la app sin saber de dónde vienen (Red o Local).

¿Para qué se usa?

Para aplicar Inversión de Dependencia. El dominio dicta las reglas, la capa de data las obedece. 

// Contrato puro en Domain
interface ProductRepository {
    suspend fun getProducts(): List<Product>
}
Domain: UseCase

Use Cases

¿Qué es? Una clase que representa una única acción de negocio.

  • Solo tienen 1 responsabilidad.
  • Orquestan varios repositorios si es necesario.
  • Usan el operador invoke. 
class GetProductsUseCase(
    private val repo: ProductRepository
) {
    // Operador que permite llamar: 
    // useCase()
    suspend operator fun invoke(): List<Product> {
        return repo.getProducts()
    }
}

🎭 Use Cases: ¿Cuándo crearlos?

No todos los casos necesitan un UseCase. Aquí está el criterio:

✅ CREAR UseCase cuando:

  • • Hay lógica de negocio (validaciones, cálculos, reglas)
  • • Se combinan múltiples repositorios
  • • La operación es reutilizable en varias pantallas
  • • Necesitas transformar datos de forma compleja
  • • Quieres testear la lógica independientemente

❌ NO crear UseCase cuando:

  • • Solo es un CRUD simple sin lógica (ej: getUserById)
  • • Solo delega al repository sin agregar valor
  • • La operación no se reutiliza nunca
  • • Es un getter directo de datos
En estos casos, el ViewModel puede llamar directamente al Repository

❌ UseCase innecesario (solo delega) 

class GetProductByIdUseCase(
    private val repo: IProductRepository
) {
    suspend operator fun invoke(id: String): Product {
        return repo.getProductById(id)
        // 🚨 No aporta nada de valor
        // 🚨 Solo es un "pass-through"
    }
}

// ViewModel
class ProductDetailViewModel(
    private val useCase: GetProductByIdUseCase
) {
    fun loadProduct(id: String) {
        // Mejor llamar directo al repo
    }

Domain: Model

Models (Entities)

¿Qué es? Son las clases que representan los conceptos principales del negocio. Son puros, sin dependencias técnicas.

  • Definen la estructura de datos del negocio
  • Contienen validaciones y reglas de negocio
  • Son 100% independientes de frameworks
  • Compartidos entre todas las plataformas (KMP)

¿Por qué en Domain?

Porque representan la "verdad" del negocio. No deben cambiar si cambiamos la base de datos, la API o la UI. 

// shared/src/commonMain/kotlin/domain/model
data class Product(
    val id: String,
    val name: String,
    val description: String,
    val price: Double,
    val imageUrl: String,
    val category: Category,
    val inStock: Boolean
) {
    // Reglas de negocio
    fun isValidForSale(): Boolean {
        return name.isNotBlank() && 
               price > 0 && 
               inStock
    }
    
    fun getFormattedPrice(): String {
        return "$%.2f".format(price)
    }
}

data class Category(
    val id: String,
    val name: String
)

// ✅ Puro Kotlin, sin Android/iOS dependencies
// ✅ Compartido 100% en KMP
// ✅ Testeable sin infraestructura

Data: Repository Implementation

Repository Implementation

¿Qué es? Es la clase concreta que implementa el contrato del Repository definido en Domain.

  • Implementa la interface del Domain
  • Conecta con APIs, bases de datos, caché
  • Maneja errores y estados de red
  • Siempre retorna modelos de Domain (nunca DTOs)

¿Por qué en Data?

Porque contiene detalles técnicos (Ktor, SQL) que no deben contaminar el Domain puro. 

// shared/src/commonMain/kotlin/data/repository
class ProductRepositoryImpl(
    private val apiService: KtorApiService,
    private val mapper: ProductMapper
) : ProductRepository {

override suspend fun getProducts(): List<Product> {
    // 1. Obtenemos datos crudos (DTOs)
    return try {
        apiService.fetchProducts()
            .map { dto -> 
                // 2. Convertimos a Domain
                dto.toDomain() 
            }
    } catch (e: Exception) {
        // 3. Manejo de errores
        throw DataException("Failed to fetch products", e)
    }
}

override suspend fun getProductById(id: String): Product {
    val dto = apiService.fetchProductById(id)
    return dto.toDomain()
}
}

// ✅ Implementación concreta
// ✅ Conecta con APIs
// ✅ Siempre retorna Domain models
Data: DataResource

DataResource / Data Source

¿Qué contiene? Los DataResources son responsables de obtener y almacenar datos desde fuentes técnicas: Remote (APIs), Local (DB), y Cache. Orquestan llamadas, manejan paginación, retries, autenticación y adaptan el formato crudo hacia DTOs.

  • • RemoteDataSource: Llama a `ApiService` y devuelve DTOs.
  • • LocalDataSource: Lee/Escribe en la base de datos (Room/SQL).
  • • Cache: Memoria temporal para performance y offline.
  • • Coordinador: Decide cuándo usar Remote vs Local y aplica políticas.
  • • Responsable de conversiones técnicas (formato, headers, tokens).

Buena práctica

Mantener DataResources delgados: devolver DTOs o respuestas técnicas; dejar la conversión a Domain en Mappers/Repository impl.

// Ejemplo: Remote DataSource (interfaz)
interface ProductRemoteDataSource {
    suspend fun fetchProducts(): List<ProductDto>
    suspend fun fetchProductById(id: String): ProductDto
}

// Implementación usa ApiService internamente
class ProductRemoteDataSourceImpl(private val api: KtorApiService): ProductRemoteDataSource {
    override suspend fun fetchProducts() = api.fetchProducts()
    override suspend fun fetchProductById(id: String) = api.fetchProductById(id)
}

// ✅ Separación clara: ApiService = cliente HTTP, DataSource = lógica de acceso
Data: Models / DTOs

Modelos de Transporte (DTOs)

¿Qué son? DTOs representan exactamente cómo vienen los datos desde la API o la BD. Son serializables y pueden contener campos nulos o formatos distintos al Domain.

  • • Diseñados para transporte/serialización.
  • • Pueden tener nombres distintos y tipos laxos (ej. número como String).
  • • No deben escapar al Domain: mapearlos siempre a Models puros.
  • • Mantener validaciones y normalizaciones fuera del Domain (en Mappers).

Regla

DTO → Mapper → Domain Model. Nunca usar DTOs directamente en UseCases o ViewModels.

// shared/src/commonMain/kotlin/data/dto
@Serializable
data class ProductDto(
    val id: String? = null, // Puede venir null
    val product_name: String,
    val price: String, // A veces viene como String
    val image_url: String? = null,
    val category_info: CategoryDto?
)

@Serializable
data class CategoryDto(
    val cat_id: String,
    val cat_name: String
)

// Cliente HTTP (ApiService) devuelve DTOs
class KtorApiService(private val httpClient: HttpClient) {
    suspend fun fetchProducts(): List<ProductDto> = httpClient.get("/products").body()
    suspend fun fetchProductById(id: String): ProductDto = httpClient.get("/products/$id").body()
}
Data: Mappers

Mappers

¿Qué es? Traduce entre capas: DTO ↔ Domain ↔ Presentation. Se asegura de normalizar formatos, validar campos y mantener invariantes.

Buenas prácticas

  • • Mappers puros y testeables (sin efectos secundarios).
  • • Manejar nulls y formatos inconsistentes aquí, no en el Domain.
  • • Mapear tanto DTO → Domain como Domain → DTO cuando sea necesario.
  • • Mantener mapeos simples; extraer transformaciones complejas a helpers. 
// DTO -> Domain
fun ProductDTO.toDomain(): Product {
    return Product(
        id = id,
        title = title,
        price = Price(
            amount = (price * 100).toLong(),
            currency = "USD"
        ),
        description = description,
        category = category,
        image = image

    )
}

Domain Model vs Data Model

Domain Model (Modelos de negocio)

  • • Representan la "verdad" del negocio (invariantes).
  • • Tipos seguros y no nulos cuando corresponde.
  • • Métodos y validaciones (reglas de negocio).
  • • Independientes de APIs, BD o UI.

Data Model / DTO (Modelos de transporte)

  • • Formato crudo venido de la API o BD (nombres y tipos distintos).
  • • Campos opcionales, nulos o formatos inconsistentes.
  • • Pensados para transporte/serialización, no para reglas.
  • • Cambian cuando la API cambia.

¿Por qué usar DI?

Sin DI (Caos)

Las clases crean sus propias dependencias. Si cambias un motor de base de datos, tienes que modificar 20 archivos. Acoplamiento total.

Con DI (Orden)

Las clases solo piden lo que necesitan. Koin centraliza la creación. Cambiar una implementación es tocar un solo archivo.

La DI explicada con ejemplos reales

Electricidad

El enchufe no depende de si la energía es solar, eólica o térmica. Solo necesita que cumpla el estándar.

Lámpara

La lámpara no fabrica su propia bombilla; recibe una que encaje en el socket (la interfaz).

Restaurante

El comensal pide un plato, no depende de qué cocinero específico esté en la cocina ese día.

Eso es DI: tú pides lo que necesitas, alguien más te lo entrega.

Conceptos Clave en Koin

single { ... }

Crea un Singleton. La misma instancia vive durante todo el ciclo de vida de la app.

single { ProductApiService(get()) }

factory { ... }

Crea una nueva instancia cada vez que se solicita. No guarda estado.

factory { GetProductsUseCase(get()) }

Organización de Módulos

// Separar los módulos por capas refuerza la arquitectura
val dataModule = module {
single { ProductApiService(get()) }
single<ProductRepository> { ProductRepositoryImp(get()) }
}

val domainModule = module {
factory { GetProductsUseCase(get()) }
}

val viewModelModule = module {
viewModel { ProductViewModel(get()) } // Inyecta el Caso de Uso
}

El punto de arranque 

// CommonMain: Estructura compartida
fun initKoin(appDeclaration: KoinAppDeclaration = {}){
  startKoin {
      appDeclaration()
      modules(dataModule, domainModule, viewModelModule)
  }
}

// iOS: initKoin() desde Swift al arrancar la App

Presentation: ViewModel

El ViewModel en KMP

¿Qué es? Es el encargado de mantener el estado de la UI y gestionar los eventos del usuario. No sabe nada de la plataforma (Android/iOS), solo de lógica de presentación.

  • Expone el estado mediante StateFlow.
  • Llama a los Use Cases para obtener datos.
  • Sobrevive a cambios de configuración.

Regla de Oro:

El ViewModel recibe Modelos de Dominio y los transforma en UI State para que la pantalla los dibuje fácilmente.

class ProductViewModel(
    private val getProducts: GetProductsUseCase
) : ViewModel() {

    // Estado expuesto a la UI
    private val _state = MutableStateFlow(UiState())
    val state = _state.asStateFlow()

    fun load() = viewModelScope.launch {
        _state.update { it.copy(isLoading = true) }
        val result = getProducts()
        _state.update { it.copy(
            products = result, 
            isLoading = false
        )}
    }
}
Presentation: UI (Screens)

La UI (Screens)

¿Qué es? Es la implementación visual (Compose en Android o SwiftUI/Compose en iOS). Su única misión es observar el estado y notificar eventos.

Declarativa Se reconstruye automáticamente cuando el estado cambia.
Pasiva No decide qué mostrar; solo obedece al UI State. 
@Composable
fun ProductScreen(viewModel: ProductViewModel) {
    // Observamos el estado del ViewModel
    val state by viewModel.state.collectAsState()

    if (state.isLoading) {
        LoadingSpinner()
    } else {
        ProductList(
            items = state.products,
            onItemClick = { viewModel.onSelect(it) }
        )
    }
}

UI Components

Atómicos

Botones, textos y tarjetas pequeñas que no conocen al ViewModel. Son 100% reutilizables.

Stateless

Reciben datos por parámetros y devuelven clicks por lambdas. Fáciles de testear y de ver en Previews.

Cohesión

Agrupan lógica visual común para mantener las Screens limpias y legibles.

// Ejemplo de Componente Stateless (Sin estado interno)
@Composable
fun ProductCard(product: Product, onClick: () -> Unit) {
    Card(modifier = Modifier.clickable { onClick() }) {
        Text(text = product.name)
        Text(text = product.getFormattedPrice())
    }
}

Código repetitivo y necesario pero que no aporta lógica real (ej. getters, configuraciones).

Service Locator

Patrón que usa Koin para centralizar y "prestar" las dependencias de la app.

LaunchedEffect

Efecto de Compose que ejecuta código (como cargar datos) cuando el componente entra en pantalla.

Sealed Interface

Interfaz cerrada que obliga a manejar todos sus estados (ej. UIState: Loading, Success, Error).

State Hoisting

Técnica de subir el estado de un componente a su padre para hacerlo más reutilizable y testeable.

Suspend Function

Función que puede pausarse (sin bloquear el hilo) mientras espera una respuesta (ej. de internet).

Glosario Técnico (Parte 2)

KMP

Kotlin Multiplatform. Compartir lógica entre Android, iOS, Web y Desktop.

DTO

Data Transfer Object. La forma cruda en que los datos llegan de la API.

Expect / Actual

Mecanismo de KMP para definir código compartido que necesita implementación nativa en cada plataforma.

Ktor

El cliente HTTP oficial de Kotlin para realizar peticiones de red multiplataforma.

Compose Multiplatform

Framework declarativo para crear UIs que corren en múltiples sistemas operativos.
